# Как изменение кода доезжает до OrbStack — подробный путь для начинающих

> Этот документ — отдельный «учебник» к [RUN.md](./RUN.md). RUN.md отвечает на
> вопрос «какие команды нажать», а здесь — «почему это работает»: что такое
> Helm и ArgoCD, что происходит на каждом этапе, и как правка цвета кнопки в
> React-коде превращается в новую версию приложения, открытую в браузере.
>
> Все команды и файлы упомянуты так, как они лежат в репозитории — можно
> открывать параллельно и сверяться.

---

## 1. Картина целиком

Когда вы правите код и запускаете две команды, происходит вот что:

```
 MacBook (вы)                                OrbStack-машина (Ubuntu 24.04)
 ─────────────────────────────────────       ─────────────────────────────────
 1. правите код в react-front/src/
 2. git commit
 3. ./scripts/orbstack-local-git.sh
        │
        │  git push (по файловой системе
        │  /mnt/mac — это почти мгновенно)
        ▼
    .local/gitops-origin.git  ──────────►  git daemon (порт 9418 внутри машины)
    (голый git-репозиторий                        │
     на Mac, .local/gitignored)                   ▼
                                          4. ArgoCD (работает в кластере k3s)
                                             каждые ~3 мин: «что в git?»
                                             «что в кластере?» — сравнивает
                                             для рендера запускает Helm:
                                             helm secrets template …
                                             (секреты расшифровывает SOPS)
                                             │
                                             ▼
                                          5. новые YAML-манифесты ≠ то, что
                                             в кластере → ArgoCD применяет их
                                             (kubectl apply)
                                             │
                                             ▼
                                          6. k3s: новый ReplicaSet → новые
                                             поды → тянут образ → запускаются
                                             │
                                             ▼
                                          7. браузер на Mac: grogu.test
                                             → ingress → новая версия
```

Ключевая идея (она называется **GitOps**): *git-репозиторий — источник
истины*. Мы не командуем кластеру «задеплой», мы публикуем желаемое
состояние в git, а ArgoCD приводит кластер в соответствие с ним — сам, без
участия человека, и так же сам откатывает всё назад, если состояние в git
вернуть.

## 2. Словарь: пять слов, без которых дальше никуда

**Kubernetes (в нашем случае — его легковесная сборка k3s)** — система,
которая запускает приложения в виде **контейнеров** (Docker-образов) на наборе
машин и следит, чтобы они жили: упал контейнер — перезапустит, стало мало
экземпляров — добавит. Единица запуска — **под** (pod): один или несколько
контейнеров + их настройки. Над подами стоят **Deployment** (описание «хочу 2
экземпляра такого контейнера»), **Service** (внутренний адрес группы подов) и
**Ingress** (правила «какой адрес на какой сервис отправлять»).

**Helm** — «пакетный менеджер» для Kubernetes. Kubernetes-манифесты — это
много похожих YAML-файлов; Helm позволяет собрать их в один **чарт** (chart)
с шаблонами и переменными. У нас чарт лежит в `helm-chart/`:

- `helm-chart/Chart.yaml` — название и версия чарта;
- `helm-chart/values.yaml` — **все настройки** (версии образов, имена
  доменов, пароли-заглушки): `https://github.com` тут нет, это просто YAML;
- `helm-chart/templates/` — шаблоны: обычные Kubernetes-YAML, в которых
  значения подставляются из values (например,
  `helm-chart/templates/react-front/react-front-deployment.yaml`);
- при установке чарта Helm подставляет значения и отдаёт кластеру готовые
  манифесты. Один запуск установки называется **релизом** — у нас он
  называется `ap` (важно: имя `ap` используется в шаблонах, не меняйте).

**ArgoCD** — «GitOps-робот», работающий внутри кластера. Он умеет:

1. следить за git-репозиторием (какой — написано в специальном объекте
   `Application`, у нас это `gitops/apps/orbstack/ap.yaml`);
2. **рендерить** содержимое (у нас — запускать Helm с нужными values-файлами)
   и получать на выходе список манифестов: «вот как должно выглядеть»;
3. сравнивать с тем, что реально работает в кластере;
4. **применять разницу** (это называется *sync*), если включён автоматический
   режим — а у нас включён.

Всё вместе это даёт магию, которую вы уже видели: закоммитил — через пару
минут приложение в кластере само изменилось.

**SOPS + helm-secrets** — система секретов. Реальные пароли (база данных,
админ Keycloak) лежат в `secrets.yaml` в **зашифрованном** виде прямо в
репозитории (ключ шифрования — тоже в репозитории, `demo-secret-key.asc` —
это демонстрационный проект, ключ публичный намеренно). ArgoCD перед рендером
расшифровывает файл и подставляет значения; в кластере секреты появляются уже
расшифрованными, но в git их открытыми никто не видел.

**Ansible** — система автоматизации настройки Linux-машин. В этом проекте она
один раз готовит машину: ставит обновления, создаёт пользователя, настраивает
файрвол, ставит k3s, ingress-nginx и сам ArgoCD. За это отвечают файлы в
`ansible/` (например, `ansible/roles/k3s/tasks/main.yml`). Ansible
запускается на этапе `./start orbstack` и дальше в everyday-цикле не нужен.

## 3. Карта репозитория: какой файл за что отвечает

| Файл | Что это |
|---|---|
| `helm-chart/values.yaml` | базовые настройки всего стека (версии образов, домены, ресурсы) |
| `helm-chart/values-orbstack.yaml` | дополнение настроек именно для OrbStack (домены `*.test`, TLS off) |
| `helm-chart/templates/` | шаблоны манифестов всех компонентов (front, gateway, backends, postgres, redis, keycloak, ingress…) |
| `helm-chart/secrets.yaml` (в корне репо — `secrets.yaml`) | зашифрованные пароли (SOPS) |
| `gitops/apps/orbstack/ap.yaml` | **объект Application для ArgoCD**: какой репозиторий, какая ветка, какие values-файлы использовать |
| `react-front/` | исходники React-приложения (то, что вы видите в браузере) |
| `react-front/Dockerfile` | как из исходников собирается образ фронта |
| `nodejs-back/`, `golang-back/` | исходники двух API-бэкендов |
| `helm-chart/config/krakend.json` | конфиг API-шлюза KrakenD (маршруты `/api/...`) |
| `helm-chart/config/realm-export.json` | настройки Keycloak: realm, пользователь demo, клиент reactclient |
| `ansible/` | автоматическая настройка машины (k3s, ingress-nginx, ArgoCD) |
| `scripts/orbstack-create.sh` | одна команда «создать машину с нуля» |
| `scripts/orbstack-local-git.sh` | «доставка» ваших коммитов до ArgoCD без GitHub |
| `scripts/local-up.sh` | то же самое, но для локального Minikube (простой режим без ArgoCD) |

## 4. Кто и что поставил в машине (контекст, один раз)

Команда `./start orbstack` запускает Ansible-плейбук `ansible/site.yml`,
который по ролям готовит машину:

1. `common` — обновления, пользователь `deploy`, файрвол (ufw: открыты только
   22/80/443), fail2ban, отключение swap;
2. `k3s` — установка самого Kubernetes одной командой;
3. `ingress_nginx` — контроллер Ingress: именно он слушает порты 80/443
   **на самой машине** и маршрутизирует запросы по имени хоста;
4. `argocd` — установка ArgoCD + подключение helm-secrets-плагина (побочный
   контейнер в поде `argocd-repo-server`, который умеет расшифровывать SOPS)
   + создание **корневого Application** (app-of-apps), который указывает на
   `gitops/apps/orbstack` в git.

После этого машина — это маленький, но настоящий Kubernetes-кластер, и дальше
всё работает по законам GitOps.

## 5. Сквозной пример: «хочу изменить кнопку»

Допустим, в приложении не нравится кнопка «fetch data» — например, хотим
поменять её цвет на зелёный. Вот **полный** путь изменения, по шагам.

### Шаг 1. Находим код кнопки

Кнопка живёт в исходниках фронта: `react-front/src/App.tsx`, строка 60:

```tsx
<Button onClick={handleClickFetchButton}>fetch data</Button>
```

Правим, например, на:

```tsx
<Button style={{ background: 'green' }} onClick={handleClickFetchButton}>
  fetch data
</Button>
```

Можно проверить локально (не обязательно, но удобно): `cd react-front &&
npm install && npm run dev` — Vite поднимет дев-сервер, обычно на
`http://localhost:5173`. Это **не** кластер — просто быстрый предпросмотр
кода в браузере.

### Шаг 2. Понимаем главное: кластер не собирает код

Kubernetes не умеет брать TypeScript и «применять» его. Он умеет только
запускать **готовые Docker-образы**. Поэтому любое изменение кода приложения
(в отличие от изменения настроек в `values.yaml`) должно сначала стать новым
образом. Так устроено везде — и в OrbStack, и в VPS, и в любой компании.

Сборка описана в `react-front/Dockerfile`: берётся `node:20-alpine`,
ставятся зависимости, `npm run build` компилирует React в статику, готовая
статика кладётся в образ. Заодно внутрь «запекаются» адреса Keycloak
(`VITE_KEYCLOAK_URL` и пр.) — поэтому у фронта версия образа меняется при
каждой сборке, а не берётся «последняя».

### Шаг 3. Собираем новый образ

```bash
cd react-front
docker build -t mmko67/grogu-front:0.3.7 .
```

(`0.3.7` — следующая версия; текущая указана в `helm-chart/values.yaml`,
поле `front.version: 0.3.6`. Номер инкрементируем каждый раз.)

Здесь есть развилка — **куда деть образ**, чтобы машина его увидела:

- **Путь «как в проде»**: `docker push mmko67/grogu-front:0.3.7` — образ
  уезжает в Docker Hub, и кластер скачает его оттуда при деплое. Именно так
  работает `./start lan` / `./start vps`.
- **Путь «совсем локально, без Docker Hub»**: сохранить образ в файл и
  импортировать его в к3s внутри машины напрямую:
  ```bash
  docker save mmko67/grogu-front:0.3.7 | \
    ssh ubuntu@192.168.139.195 'sudo k3s ctr images import -'
  ```
  (IP машины печатает `./scripts/orbstack-local-git.sh`.) Тогда кластер
  найдёт образ у себя локально и ничего никуда не отправляет.

### Шаг 4. Говорим чарту, что теперь нужна новая версия

Открываем `helm-chart/values.yaml` и меняем:

```yaml
front:
  version: 0.3.7      # было 0.3.6
```

Это то самое место, где «код» превращается в «конфигурацию для Helm»: шаблон
`helm-chart/templates/react-front/react-front-deployment.yaml` подставит эту
версию в поле `image:` у Deployment. Когда ArgoCD увидит новый `image:`,
k3s поймёт: «версия изменилась» — и запустит перекат (rolling update): поднимет
под с новым образом, дождётся готовности, убьёт старый.

### Шаг 5. Коммитим

```bash
git add -A
git commit -m "кнопка fetch data стала зелёной (front 0.3.7)"
```

Пока это просто локальный коммит — кластер про него не знает.

### Шаг 6. Доставляем коммит до ArgoCD — `git push gitea main`

Локальный CI-режим устроен как «GitHub, живущий у вас на Mac»:

- **Gitea** (git-сервер с веб-интерфейсом) — контейнер на Mac,
  `http://localhost:3000`; поднимается скриптом `scripts/orbstack-gitea.sh`;
- **act_runner** — CI-раннер Gitea Actions (рядом с Gitea); он выполняет
  пайплайн из `.gitea/workflows/build-deploy.yml` — синтаксис тот же, что у
  GitHub Actions, поэтому переход на GitHub позже — это переименование папки
  и смена адресов;
- **registry:2** — хранилище образов **внутри машины k3s** (порт 30500);
  поднимается `scripts/orbstack-registry.sh`. Это локальный «Docker Hub»:
  кластер сам скачивает образы из него (зеркало настроено в
  `/etc/rancher/k3s/registries.yaml`).

Что делает `git push gitea main`:

1. коммит попадает в Gitea;
2. Gitea Actions запускает пайплайн: определяет, какие сервисы изменились
   (по путям `react-front/`, `nodejs-back/`, `golang-back/`), собирает
   **только их** образы и пушит их в registry с тегом = короткий git-SHA
   (неизменяемые теги — как в проде);
3. ботом-коммитом обновляет версии образов в `helm-chart/values.yaml`
   (`[skip ci]`, чтобы не зациклиться);
4. зеркалирует `main` в репозиторий, который смотрит ArgoCD
   (`.local/gitops-origin.git` через git-daemon в машине).

Дальше всё идёт, как описано в шагах 7–8: ArgoCD рендерит Helm, видит новые
версии образов, применяет — и приложение обновляется само. Итог: вы трогаете
только бизнес-код, остальное делает пайплайн.

### Шаг 7. ArgoCD замечает изменения (автоматически, до ~3 минут)

ArgoCD каждые ~3 минуты проходит цикл **reconciliation** («сверка»):

1. **Корневой Application** (его создал Ansible) указывает на папку
   `gitops/apps/orbstack` в нашем git-репозитории. ArgoCD читает оттуда файл
   `ap.yaml` — и следит, чтобы в кластере существовал дочерний `Application`
   с именем `ap` ровно с такими настройками.
2. **Application `ap`** говорит: рендери содержимое папки `helm-chart` из
   репозитория с помощью плагина. Плагин — это побочный контейнер в поде
   `argocd-repo-server` (его настройка — `ansible/roles/argocd/templates/`),
   который выполняет команду:

   ```bash
   helm secrets template ap . -f ../secrets.yaml -f values-orbstack.yaml \
     --namespace default
   ```

   Расшифровка: «Helm, отрендери чарт в текущей папке, взяв общие настройки
   из `values.yaml`, плюс секреты из расшифрованного `secrets.yaml`, плюс
   orbstack-настройки из `values-orbstack.yaml`». Команда `secrets` — это
   плагин helm-secrets: перед рендером он расшифровывает SOPS-файлы (для
   этого в контейнере установлен наш demo GPG-ключ).

3. На выходе — «манифесты»: полный список YAML-объектов, которые **должны**
   существовать в кластере (Deployments, Services, Ingress, ConfigMaps,
   Secrets…). Всё, что зашито в чарте, становится конкретикой.

### Шаг 8. Сравнение и применение (sync)

ArgoCD берёт этот список и сравнивает с реальностью в кластере:

- «в git у Deployment фронта образ `:0.3.7`, а в кластере крутится `:0.3.6`» —
  **разница есть**;
- статус приложения становится `OutOfSync`, и, так как в `ap.yaml` включён
  автоматический режим (`syncPolicy.automated`), ArgoCD сразу запускает
  **sync**: применяет изменённые манифесты (по сути выполняет kubectl apply).

За этим наблюдает уже сам k3s: Deployment получает новый ReplicaSet, тот
создаёт под с образом `0.3.7`, под проходит проверки готовности, старый под
гасится. Через несколько секунд кластер снова «совпадает с git» — статус
становится `Healthy/Synced`. Это и есть та самая пара статусов, которую вы
видели в выводе `./start orbstack`.

Полезно знать: у sync-политики включены `prune: true` (удалишь объект из
чарта — он удалится из кластера) и `selfHeal: true` (изменишь что-то руками
в кластере — ArgoCD вернёт как в git). Именно поэтому «ручные» правки в
orbstack-кластере бессмысленны — и это хорошо: кластер всегда воспроизводим
из git.

### Шаг 9. Браузер показывает новую кнопку

Открываете `http://grogu.test/`. Цепочка такая:

1. `/etc/hosts` на Mac направляет `grogu.test` → `192.168.139.195` (IP
   машины — его печатает `orbstack-local-git.sh`);
2. запрос прилетает на порт 80 машины, где его встречает ingress-nginx и по
   заголовку `Host: grogu.test` отправляет на Service реакта;
3. React-приложение грузится уже **новое** — с зелёной кнопкой. Если
   картинка не поменялась — это почти всегда кэш браузера: Cmd+Shift+R
   (жёсткое обновление).

Готово: правка в коде прошла весь путь — git → ArgoCD → Helm → k3s →
браузер, и на каждом этапе её можно было наблюдать (см. раздел 7).

## 6. А если меняю не код, а настройки? (самый быстрый путь)

Не всё требует пересборки образов. Вот что доезжает **только через git**,
без `docker build`:

| Что меняете | Где | Пример |
|---|---|---|
| Настройки стека | `helm-chart/values.yaml` или `values-orbstack.yaml` | домены, ресурсы подов, `metrics.enabled` |
| Конфиг шлюза | `helm-chart/config/krakend.json` | новые маршруты `/api/...` |
| Настройки Keycloak | `helm-chart/config/realm-export.json` | новый пользователь, клиент |
| Любые манифесты | `helm-chart/templates/**` | переменные окружения, пробы готовности |

Путь тот же: коммит → `./scripts/orbstack-local-git.sh` → ArgoCD → sync.
Разница в одном: на шаге 3 не нужен новый Docker-образ (меняется конфигурация
запуска, а не код внутри образа). Под перезапустится только если изменилось
что-то в его манифесте (например, env или image).

## 7. Где смотреть, что происходит (шпаргалка наблюдения)

| Хочу увидеть | Команда (на Mac, из репозитория) |
|---|---|
| Статус приложения ArgoCD | `make status TARGET=orbstack` |
| Поды приложения | `orb -m k3s-orbstack -u ubuntu sudo k3s kubectl get pods` |
| Логи пода | `orb -m k3s-orbstack -u ubuntu sudo k3s kubectl logs deploy/react-front-deployment` |
| Что ArgoCD думает об `ap` | `orb -m k3s-orbstack -u ubuntu sudo k3s kubectl -n argocd get application ap` |
| Красивый веб-интерфейс ArgoCD | добавьте `192.168.139.195 argocd.test` в `/etc/hosts` и откройте `http://argocd.test/`; пароль: `cat .local/argocd-orbstack-admin-pw` |
| Предпросмотр манифестов ДО коммита | `cd helm-chart && helm template ap . -f values.yaml -f values-orbstack.yaml \| less` |
| Кто из них «не в порядке» | `orb -m k3s-orbstack -u ubuntu sudo k3s kubectl get events --sort-by=.lastTimestamp \| tail` |

Статусы ArgoCD, которые встретитесь:

- `Synced` — в кластере ровно то, что в git;
- `OutOfSync` — есть разница, автоматика скоро применит;
- `Unknown` / `ComparisonError` — не удалось даже сравнить (чаще всего
  ошибка рендера: смотрите условия приложения или логи sidecar);
- `Healthy` / `Missing` / `Degraded` — состояние ресурсов: поднялись /
  ещё не созданы / что-то не так.

## 8. Как откатить изменение

Так же, как внести — через git:

```bash
git revert <коммит>            # или вручную верните старое значение и закоммитьте
./scripts/orbstack-local-git.sh
```

ArgoCD увидит «в git теперь старая версия» и сам перекатит кластер назад.
Никаких отдельных «откатов деплоя» не существует — откат это тоже коммит.
(Единственное исключение — данные в PostgreSQL: они не в git и `revert` их
не возвращает.)

## 9. Частые вопросы новичка

**Внес изменение, а в кластере ничего не поменялось.**
Чек-лист: (1) коммит сделан? `git log -1`; (2) запускали
`./scripts/orbstack-local-git.sh` после коммита? (3) прошло ~3 минуты? (4)
`make status TARGET=orbstack` — приложение в статусе? (5) если меняли код —
собрали **новый** образ и подняли версию в `values.yaml`? (ArgoCD не умеет
«угадывать», что образ надо пересобрать — он видит только git.)

**Под перезапустился, хотя я менял только конфиг.**
Это нормально: перезапуск — способ донести новый конфиг до процесса. Helm
меняет поле в манифесте пода → k3s обязан пересоздать под с новым
содержимым.

**Где жить без GitHub — это «по-настоящему»?**
Да. Схема «репозиторий, из которого ArgoCD читает состояние» не обязана быть
на GitHub — это может быть любой git-сервер. В rehearsal-режиме это `git
daemon` на самой машине; в проде (vps) — GitHub. Протокол и шаги ArgoCD
одинаковы.

**Почему для кнопки нужен новый образ, а для маршрута шлюза — нет?**
Потому что образ — это «замороженный» код приложения (фронт собран в статику
ещё на этапе `docker build`), а `krakend.json` / `values.yaml` — это
конфигурация, которую чарт передаёт при запуске. Меняется конфигурация —
достаточно git; меняется код — нужен новый образ.

**Что за `sha`-подобные статусы `Healthy/Synced` в выводе `./start
orbstack`?**
Это и есть «кластер совпадает с git» — финальное состояние, ради которого всё
затевалось.
